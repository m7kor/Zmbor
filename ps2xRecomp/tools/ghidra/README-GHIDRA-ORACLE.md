# Ghidra headless oracle pipeline (Phase 19, ADOPTED for functions only)

Ghidra is an **optional, external oracle** for function discovery. It never
replaces Zmbor's own discovery: a Ghidra map is optional input, loaded
through the real `ElfParser::loadGhidraFunctionMap` path, and merged under
the existing strict precedence **symbols > Ghidra map > config extras >
discovered**. A map is never required, and a bad map row never becomes a
function (see "Validation gate" below).

## What is adopted, and what is not

- **ADOPTED:** the functions-only headless export
  (`ExportPS2FunctionsHeadless.java` in this directory) as a standard,
  documented step, exactly as below.
- **REJECTED:** the label-collection port (executable labels,
  materialised addresses, data pointers). Phase 19 built it, measured it
  on the POC 1 corpus, and rejected it: 19 label rows, **0 true
  positives, 19 false positives** (2 switch blocks + 17 intra-function
  branch targets), while Ghidra's function recovery already covered 100%
  of known functions. Label rows share the CSV format, and `entry_*`
  names are not auto-generated per `IsAutoGeneratedName`, so the loader
  promotes them as named extras — the label feed cannot be filtered by
  the loader. Do not feed a label export to the loader. The port and its
  measurement are kept as a Phase 19 artifact outside this tree, not as
  a pipeline input.

## Prerequisites

- Ghidra 12.1.4 (verified version; other 12.x releases are untested
  here), OpenJDK 21 (verified 21.0.12.1).
- The Emotion Engine language extension (`ghidra-emotionengine-reloaded`,
  HEAD `4c787f8` in the POC 1 runs) installed in the Ghidra
  installation. Without it the `r5900` language id does not exist and
  the import fails. That failure is itself a result: record it, do not
  silently fall back to generic MIPS. Do not claim PS2-specific
  instruction support merely because a tool supports generic MIPS.

## Step 1 — export functions headlessly

```sh
analyzeHeadless <projDir> <projName> -import <elf> -overwrite \
  -processor r5900:LE:32:default \
  -scriptPath ps2xRecomp/tools/ghidra \
  -postScript ExportPS2FunctionsHeadless.java <out.csv>
```

The script prints `Exported N functions to <out.csv>` on success. The
CSV contract is `Name,Start,End,Size` (one header line, then one row
per function). Ends are Ghidra body-max+1 (exclusive). The `Size`
column is the body address count, **not** a byte size (on the synthetic
fixture, `f_switch` spans 112 bytes but reports 76 — its body excludes
the jump-table cases), and the loader ignores it; only `Start`/`End`
matter.

Number formats (Gate D): `Start` and `End` are `0x`-prefixed hex
(the exporter writes `%08X` with a `0x` prefix) or bare decimal.
Leading-zero octal is **not** supported: a bare field is always read
as decimal, so `0104` means 104 (0x68), never 8 or 68-octal. A field
that is neither clean hex nor clean decimal makes the whole row
malformed (counted, warned, skipped). The loader also enforces a
262,144 data-row cap (a clear warning when exceeded; rows past the
cap are never read) and a 4,096-character per-line cap (over-long
lines are malformed). A real Ghidra export for a PS2 title holds tens
of thousands of functions at most, so neither cap binds a legitimate
export; both exist so a corrupt file cannot turn the load into an
unbounded read. CRLF line endings are tolerated. The header line is
recognized by exact field names (`Name,Start,End,Size`,
case-insensitive); a file whose first line is not that header is
treated as headerless data and warns once, so a missing header can
no longer silently eat the first row.

## Step 2 — feed the CSV to the recompiler

Set the map path in the recompiler config (`ghidraMapPath`; loaded by
`PS2Recompiler::initialize` via `ElfParser::loadGhidraFunctionMap`).
Nothing else changes: existing inputs behave exactly as before when no
map is given, and the stripped e2e program still passes with Ghidra
input absent.

## Validation gate (enforced by the loader, pinned by tests)

A CSV row becomes a function only if **all** of these hold:

1. The start is inside an executable section (else skipped, counted as
   `skippedNonExecutable`, warning emitted).
2. The start is 4-byte aligned (else skipped, counted as
   `skippedMisaligned`, warning emitted — Phase 19 fix; previously
   misaligned rows were silently accepted).
3. The requested end is greater than the start (else skipped, counted
   as `skippedInvalidRange`). Gate D change: an inverted or empty
   range is **rejected**, not repaired — the shared section clamp
   used to rewrite `end <= start` to a one-instruction `[start,
   start+4)` function, which fabricated functions from inverted rows.
4. The effective end (after clamping to the section) is 4-byte
   aligned (else skipped, counted as `skippedUnalignedEnd` — Gate D).
5. Every word in `[start, end)` decodes as an R5900 instruction under
   rabbitizer (else skipped, counted as `skippedUndecodable` —
   Gate D). This is a plausibility filter, not a proof of code: an
   address-like data word decodes as a real instruction (e.g. `SD`),
   and rabbitizer is strict about nonzero unused fields, so genuine
   compiler output passes and data-in-code can still pass.
6. The row does not overlap an earlier accepted row (else skipped,
   counted as `skippedOverlapping`, first-wins — Gate D). Adjacency
   (a start exactly at the kept row's end) is not overlap. The rule
   is name-blind: it also rejects in-body label rows, which is why
   the Phase 19 label fixture was redesigned in Gate D (the two
   in-body labels are now overlap-rejected; the non-overlapping gap
   label still promotes, re-pinning the hazard).
7. The row does not start in a branch delay slot: the word at
   `start - 4` in the same section must not decode (via the project
   decoder) as an instruction with a delay slot (else skipped,
   counted as `skippedDelaySlot` — Gate D). Real function boundaries
   follow the previous function's delay slot (a nop), never sit in
   it.
8. The row parses cleanly: exactly 4 fields (a trailing comma is
   tolerated; non-empty extra content is not), and `Start`/`End`
   parse as hex-or-decimal numbers (else skipped, counted as
   `skippedMalformed`, warning emitted — Gate D; previously these
   failures skipped silently via `catch (...)`).
9. Merge precedence is respected: sized symbols override map ends, and
   when a map is loaded, discovery defers to map starts (auto-named
   extras not in the map are erased).

Every skip bucket warns, whether or not any row loaded, and the load
statistics are observable via `ElfParser::ghidraMapLoadStats()`
(`loaded`, one counter per bucket above, `headerSeen`,
`rowLimitExceeded`). A file whose rows are all rejected therefore
cannot look like a clean empty file.

The test suite pins this: `ps2_recompiler_tests.cpp` contains the
"verbatim POC 1 synthetic rows" load test (real Ghidra output, 8
functions, exact names/ranges), the misaligned / non-executable /
out-of-range mutant test, the label-promotion hazard test
(documenting that label rows *would* promote — the reason they are
never fed to the loader), and the Gate D adversarial tests (one per
gap above, each with fail-before evidence against the Phase 19
loader, plus exact skip-counter assertions).

## Measured corpus (Ghidra 12.1.4 + EE extension, headless, 2026-11-03)

| Fixture | Functions recovered | False positives |
| ------- | ------------------- | --------------- |
| synthetic stripped | 8/8 | 0 |
| basic | 7/7 | 0 |
| branchdelay | 13/13 | 0 |
| vu_macro | 7/7 | 0 |
| gs_sprite | 4/4 | 0 |

The synthetic CSV was re-verified byte-identical on a fresh re-run.
Ends: on the synthetic fixture, every CSV end equals the next
function's start except the trailing `dead_func`, whose CSV end
(`0x0010013C`, end of its own body) is 8 bytes tighter than
next-start/section-end inference (`0x00100144`, which would swallow
the non-function `bare_leaf` fragment). CSV ends are therefore
consistent with recompiler inference where comparable, and tighter and
correct for the trailing function — but only because Ghidra's bodies
are complete on this fixture. Bodies can be incomplete (tail calls,
data-in-code), so recompiler ends stay authoritative wherever a sized
symbol exists, and export ends are never silently overwritten onto
them: uncontested CSV ends survive the merge, contested ends lose to
symbols. End-exactness beyond this corpus is NOT demonstrated.

## Limitations

- The exported set is a list of function boundaries, not a
  proven-reachable set (dead functions are exported too, e.g.
  `dead_func`); Zmbor's discovery precedence and CFG validation still
  apply.
- The corpus is MIPS-subset-only synthetic + generated e2e programs.
  No real game ELF has been run through this pipeline, and no
  hardware claim is made.
- Delay-slot starts are validated by the loader since Gate D (see
  validation gate item 7). The residual gap is the decode check's
  plausibility limit (item 5): data words that decode as real
  instructions still pass.
- The loaded-map set rule is a standing semantic consequence, not a
  Gate D change: when a map is loaded, discovery admits only starts
  present in the map, so a function the map omits is dropped even if
  discovery finds it. The map is treated as the complete
  auto-function set; this is pinned by the ghidra-map fallback test
  and by the Gate D delay-slot test's set-rule assertion.
